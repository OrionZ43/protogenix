# Релиз, подпись и автообновление

## ⚠ Подпись Android — самое рискованное место проекта

**До 2026-09-11** release-сборка подписывалась debug-ключом (`signingConfig = signingConfigs.getByName("debug")` с первого коммита). Проверено 2026-09-10 (`apksigner verify --print-certs`): `build/app/outputs/flutter-apk/app-release.apk` от 2026-06-29 подписан сертификатом `CN=Android Debug`, SHA-256 `639ac6b5304831eda7a0f4d764709c4322ed0f18657015d7d6d1cf6594cd4b27`. Это ключ из `%USERPROFILE%\.android\debug.keystore` на машине Orion, созданный 2025-09-09.

Android генерирует debug-keystore **отдельно на каждой машине**. У всех одинаковы только пароль `android` и алиас `androiddebugkey`, а сам ключ у каждого свой. Поэтому:

- **Обновление ставится поверх только при той же подписи.** Смена ключа ломает обновление существующих установок: придётся удалить приложение и поставить заново.
- **Удаление приложения = потеря данных пользователя.** На Android база (`getDatabasesPath()`) и скачанная музыка (`<appDocs>/music`, `covers`, `lyrics`) лежат в приватной папке приложения и удаляются вместе с ним.
- **Подпись APK — вторая линия защиты обновлений на Android** (первая — подпись манифеста, см. ниже). С debug-ключом она держится только на секретности файла, пароль к которому знают все.
- **Первый публичный релиз ещё впереди:** на 2026-09-11 в репозитории нет ни одного тега. Установки на debug-ключе есть только у тех, кому APK передавали напрямую, — им один раз придётся переустановить приложение. Их старая обновлялка (GitHub API, сравнение тега с версией) релиз `v1.0.0` не предложит: `1.0.0` для неё не новее `1.0.0`. Следующий релиз она предложит и попробует поставить первый `.apk` из релиза — Android откажет из-за другой подписи.

**Release-ключ (решение Orion, 2026-09-11).** `android/app/build.gradle.kts` подписывает release ключом из `android/key.properties`. Этот файл есть в `android/.gitignore`, заготовку создал Claude, пароль вписывает Orion. Keystore лежит в `C:/Users/Orion Z43/.protogenix/protogenix-release.jks`, алиас `protogenix`, формат PKCS12 (один пароль на хранилище и ключ). Файл читается в UTF-8.
- Если `key.properties` или сам keystore отсутствуют, release подписывается **debug-ключом** и Gradle пишет `WARNING: android/key.properties or the keystore is missing…`. Так собираются локальные сборки, но **публиковать такой APK нельзя**. `tool/release.ps1` проверяет сертификат каждого APK (`apksigner verify --print-certs`) и не выпустит APK с другой подписью.
- **Сертификат release-ключа** (keystore создан Orion 2026-09-11): `CN=Z43 Studios, O=Z43 Studios`, SHA-256 `61502f44ef266bb7c27b5671757ca6c752a6d690d2f0d2c940a32bbdc419b0f8`. Проверено `apksigner verify --print-certs` на release-сборке 2026-09-11. Это значение записано в `$ExpectedCertSha256` в `tool/release.ps1`. Сертификат публичный (он есть в каждом APK), секрет — только keystore и пароль.
- Keystore и пароль есть только у Orion, минимум в двух местах. В git, логи и чат они не попадают. Потеря ключа означает, что ни одну Android-установку больше не обновить поверх.
- Не удалять `debug.keystore`, пока все, у кого стоит debug-сборка, не переустановили приложение.
- Google Play не используется, поэтому ключ — собственный keystore без Play App Signing.

## Обновления приложения (схема с 2026-09-11)

Код — `lib/features/updater/`, тесты — `test/features/updater/`.

- **`update_checker.dart`** при запуске качает `protogenix-update.json` по адресам из `UpdateChecker.defaultManifestUrls` (сейчас только `https://github.com/OrionZ43/protogenix/releases/latest/download/protogenix-update.json`). Он проверяет подпись (`update_envelope.dart`), сравнивает `build` манифеста с номером сборки приложения и выбирает файл по ключу платформы. Номер сборки — это `+N` из pubspec; на Windows `package_info_plus` берёт его из ProductVersion exe. Первый ответивший адрес побеждает; ошибки только пишутся в лог.
- **`update_downloader.dart`** скачивает файл по списку адресов с докачкой (HTTP Range), сверяет размер и SHA-256 (в изоляте) и не качает повторно уже проверенный файл.
- **`update_installer.dart`:**
  - Android — разрешение `REQUEST_INSTALL_PACKAGES`, затем системный установщик через `OpenFile`;
  - Windows — тихий запуск установщика Inno Setup (`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /update=1 /LOG=%TEMP%\protogenix-update.log`) и `exit(0)`;
  - остальные платформы — только ссылка на страницу релиза.
- **`update_provider.dart` и `update_banner.dart`** — баннер. «Обновить» → прогресс → установка. «Открыть», если файла для платформы нет. Обязательное обновление (сборка ниже `minSupportedBuild`) скрыть нельзя. `notes` баннер показывает простым текстом.
- **`update_manifest.dart` и `update_envelope.dart` — без Flutter-импортов:** их использует `tool/update_signing.dart` через `dart run`.

**Ключ подписи манифеста `z43-2026` вписан в `kUpdateSigningKeys` 2026-09-11**, с этого момента проверка обновлений включена. Если карта пуста, приложение не примет ни одного манифеста.

### Что должно быть в каждом GitHub Release

Всё это собирает и проверяет `tool/release.ps1` (раздел «Как выпустить релиз»).

- **`protogenix-update.json`** — подписанная обёртка `{kid, payload, signature}`: `payload` — base64 байтов `manifest.json`, `signature` — Ed25519 по этим байтам. Имя постоянное, приложение ищет файл через `releases/latest/download/`. Черновики и пре-релизы через `latest` не видны, поэтому релиз публикуется обычным.
- **Манифест** (`update_manifest.dart`) содержит поля:
  - `version` — для показа;
  - `build` — сравнение идёт только по нему, он должен расти;
  - `minSupportedBuild`, `notes`, `message`, `releaseUrl`;
  - `assets` с ключами `android-arm64-v8a`, `android-armeabi-v7a`, `android-x86_64`, `android-universal`, `windows-x64`. У каждого файла: `urls` (только https, в порядке попыток), `size`, `sha256`. Скрипт релиза кладёт все, кроме `android-x86_64`: x86_64 бывает только у эмуляторов и Chromebook, им достаётся universal.
- **`build` в манифесте = `+N` в `pubspec.yaml` той сборки, которая лежит в релизе.** Если манифест обещает сборку новее реальной, после установки приложение снова увидит «новую» версию, и получится петля. `+N` — это и Android `versionCode`: уменьшать нельзя.
- **`--split-per-abi` не использовать.** Flutter тогда ставит каждому APK свой versionCode: код ABI × 1000 + N (arm32 = 1, arm64 = 2, x86_64 = 4; `FlutterPlugin.kt`, `versionCodeOverride`). arm64-APK сборки `+1` получил бы versionCode 2001, и приложение, сравнивая его с `build` манифеста, перестало бы видеть обновления. APK под одну архитектуру собираются через `--target-platform` (раздел «Размер и совместимость сборок»).
- **Выбор файла:** на Android сначала архитектуры устройства (`supportedAbis` из `device_info_plus`), затем `android-universal`; на Windows — `windows-x64` (установщик `Protogenix-Setup-X.Y.Z.exe`).

### Ключ подписи манифеста

- **Текущий ключ** — `z43-2026`, создан Orion 2026-09-11. Приватная часть лежит в `%USERPROFILE%\.protogenix\update-signing.key`, вне репозитория, плюс резервная копия.
- **Создать ключ:** `dart run tool/update_signing.dart keygen <kid> <путь-вне-репозитория>`. Утилита откажется писать ключ внутрь репозитория и не перезапишет существующий файл (проверено 2026-09-11). Напечатанную строку с публичным ключом вписать в `kUpdateSigningKeys` (`lib/features/updater/update_keys.dart`).
- **Подписать:** `dart run tool/update_signing.dart sign <kid> <ключ> <manifest.json> protogenix-update.json`. Утилита проверяет манифест и сама сверяет получившуюся подпись.
- **Хранение.** Приватный ключ есть только у Orion, минимум в двух копиях вне репозитория.
  - Потеря ключа: ни одна установленная копия больше не примет обновление, остаётся только ручная переустановка.
  - Утечка ключа: кто-то сможет подписать свой файл. Тогда выпустить версию с новым ключом и убрать старый из `kUpdateSigningKeys`.
- **Смена ключа:** добавить новый `kid` в `kUpdateSigningKeys` рядом со старым, выпустить версию, подписанную старым ключом, а следующие подписывать новым.
- **Проверять скрипт релиза — одноразовым ключом, не настоящим:** `keygen` в папку вне репозитория, затем `tool/release.ps1 -AllowDirty -UpdateKeyPath <он> -UpdateKeyId <его kid>`. Манифест с неизвестным `kid` приложение отвергнет, так что случайно выложенный тестовый файл никому не навредит.

### Чего не делать

- Не ослаблять проверки: подпись Ed25519, адреса только по https, размер и SHA-256. На Windows это единственная защита от подменённого установщика.
- После `exit(0)` на Windows всё зависит от установщика: он должен дождаться закрытия приложения, при сбое откатиться и перезапустить приложение. Изменения в `.iss` проверять настоящим прогоном (сценарий ниже, в шаге 3 плана).
- В папку программы (`{app}`) не класть ничего пользовательского: установщик её заменяет. Данные лежат в `%LOCALAPPDATA%\Z43 Studios\Protogenix` (`data.md`).

## Как выпустить релиз (`tool/release.ps1`)

1. Поднять версию в `pubspec.yaml`: `version: X.Y.Z+N`, где N строго больше, чем у прошлого релиза (скрипт сверяет с опубликованным манифестом). Или передать скрипту `-Bump patch|minor|major` — он поднимет версию сам (ниже).
2. Написать `docs/release-notes/vX.Y.Z.md`. На GitHub он уходит целиком (markdown и HTML работают, картинки — только по абсолютным адресам, например `raw.githubusercontent.com/…/vX.Y.Z/…`). В приложение идёт только часть **до строки `<!-- more -->`**: баннер «Что нового» показывает простой текст и только первые 500 символов. Скрипт убирает из этой части HTML, картинки и разметку markdown (ссылки остаются текстом, пункты — через «•») и предупреждает, если вышло длиннее 500 символов. Без маркера в приложение уходит весь файл. Образец — `docs/release-notes/v1.0.0.md`: сверху короткое описание, под маркером — подробности.
3. Закоммитить и запушить всё. Скрипт откажется собирать из незакоммиченного кода: смотрит изменённые файлы во всём репозитории и новые неотслеживаемые в `lib/`, `android/`, `windows/`, `assets/`, `tool/`, `pubspec.*`.
4. `powershell -ExecutionPolicy Bypass -File tool/release.ps1 -NotesFile docs/release-notes/vX.Y.Z.md` — сборка и все проверки без публикации, результат в `build/release/vX.Y.Z/`.
5. То же с `-Publish`: скрипт всё пересоберёт, создаст GitHub Release `vX.Y.Z` на текущем коммите и проверит, что GitHub отдаёт новый `protogenix-update.json`.

- Нужно: Flutter, Android SDK (`sdk.dir` в `android/local.properties`), Inno Setup 6, `android/key.properties`, ключ подписи манифеста (`%USERPROFILE%\.protogenix\update-signing.key`), для `-Publish` — GitHub CLI (`winget install GitHub.cli`, затем `gh auth login`).
- Описание должно лежать в файле с именем тега, `vX.Y.Z.md`: скрипт это проверяет, чтобы релиз не ушёл со старым описанием.
- `-Bump patch|minor|major` — следующая версия (`1.0.0` → `1.0.1` / `1.1.0` / `2.0.0`), N на единицу больше и текущего, и опубликованного.
  - Скрипт пишет её в `pubspec.yaml`, всё собирает и проверяет и только потом коммитит `pubspec.yaml` вместе с описанием («release: vX.Y.Z»). С `-Publish` он пушит этот коммит в master перед созданием релиза; остальное должно быть запушено заранее (шаг 3), иначе скрипт откажется.
  - Упала сборка — `pubspec.yaml` возвращается как был, запускать снова с тем же `-Bump`. Упал push или публикация после коммита — запускать с `-Publish`, но без `-Bump`, иначе версия поднимется ещё раз.
  - С `-AllowDirty` не сочетается.
  - Проверено 2026-09-12 на временной копии репозитория с подменённым `flutter`: подсчёт версий, проверки, правка и возврат `pubspec.yaml`. Коммит, push и публикация с `-Bump` вживую ещё не запускались — первый настоящий релиз с ним проверить глазами.
- Перед релизом CI на master должен быть зелёным (`.github/workflows/ci.yml`, `dependencies.md`).
- `-MinSupportedBuild N` — сборки ниже N получат обязательное обновление (по умолчанию 1).
- `-AllowDirty` — только для проверки скрипта; вместе с `-Publish` запрещён.
- Проверки на каждый APK: сертификат release-ключа, versionCode = N, точный набор архитектур и у каждой `libflutter.so` и `libapp.so`, `zipalign -c -P 16`. Для Windows: `ProductVersion` у `protogenix.exe` = `X.Y.Z+N`. После тестовой сборки с `--build-number` в `build/windows` может остаться exe с другим номером, и без этой проверки обновление ушло бы в петлю.
- **Тестовая сборка Windows для проверки обновления:** `flutter build windows --release --build-number=0`, затем `tool/build_windows_installer.ps1 -SkipFlutterBuild`. Установленная копия с номером 0 увидит опубликованный релиз как обязательное обновление (0 < `minSupportedBuild`) и пройдёт весь путь: баннер → скачивание → тихая установка → перезапуск. Такую сборку никуда не выкладывать.
- Все `.ps1` в `tool/` — в UTF-8 с BOM (иначе Windows PowerShell 5.1 искажает русский текст).

## Размер и совместимость сборок

- **Android APK** (release-сборки 2026-09-11, release-ключ):

  | APK | Размер | Архитектуры |
  |---|---|---|
  | `android-arm64-v8a` (`--target-platform android-arm64`) | 36,8 МБ | arm64-v8a |
  | `android-armeabi-v7a` (`--target-platform android-arm`) | 34,0 МБ | armeabi-v7a |
  | `android-universal` (`flutter build apk --release`) | 105,2 МБ | arm64-v8a, armeabi-v7a, x86_64 |

  Нативные библиотеки (МБ): arm64-v8a — `libmpv.so` 11,8, `libflutter.so` 11,0, `libapp.so` 8,3, `libsqlite3.so` 1,6; armeabi-v7a — 11,2 / 8,1 / 9,1 / 1,6; x86_64 — 15,1 / 12,3 / 8,5 / 1,6. `libmpv.so` приходит из media_kit, который на Android не используется (`dependencies.md`): это 11–15 МБ в каждом APK и ~38 МБ в universal. `libsqlite3.so` нужен только для FFI на десктопе.
- **Сборка под одну архитектуру — найдено и исправлено 2026-09-11.** С `--target-platform` Flutter собирает свой движок и код приложения только под эту архитектуру, но `abiFilters` сам выставляет на все ABI (`FlutterPlugin.configureAbiWithoutSplits`). Поэтому `.so` плагинов (libmpv, libsqlite3) попадали в APK под все три архитектуры: arm64-APK весил 63,9 МБ и объявлял `native-code: 'arm64-v8a' 'armeabi-v7a' 'x86_64'`. Такой APK ставится на телефон другой архитектуры и падает при запуске: движка Flutter под неё нет. Теперь `android/app/build.gradle.kts` вырезает при упаковке ABI, которых нет в `target-platform` (`packaging.jniLibs.excludes`). Для универсальной сборки и `--split-per-abi` ничего не вырезается. `abiFilters` сам не задаём: его выставляет Flutter при подключении плагина, и результат зависел бы от порядка.
- ⚠ **Прежний замер «universal» (`app-release.apk` от 2026-06-29, 67,3 МБ) был ошибочным.** Движок Flutter и код приложения в нём есть только под arm64-v8a, под armeabi-v7a и x86_64 лежат лишь `.so` плагинов. Ровно так выглядела сборка с `--target-platform android-arm64` до исправления выше. На 32-битном телефоне тот APK встал бы и не запустился.
- **16 КБ страницы памяти (Android 15+): совместимо.** Все `.so` для arm64-v8a выровнены по LOAD ≥ 0x4000 (`llvm-readelf -lW`, 2026-09-10), `zipalign -c -P 16` проходит — скрипт релиза проверяет это на каждом APK. Перепроверять `.so` после любых изменений нативных зависимостей (media_kit, sqlite3):
  ```
  zipalign -c -P 16 -v 4 app-release.apk
  llvm-readelf -lW <lib>.so   # в строках LOAD выравнивание должно быть 0x4000 или больше
  ```
- **Android-манифест:** minSdk 24, targetSdk 36, compileSdk 36. R8 включён (`build/app/outputs/mapping/release/mapping.txt` создаётся).
- **Windows** (`flutter build windows --release`, 137 с, успешно): 83,0 МБ. `libmpv-2.dll` (28,4 МБ) и ~17,7 МБ ANGLE/SwiftShader (`libGLESv2.dll`, `d3dcompiler_47.dll`, `vk_swiftshader.dll`, `vulkan-1.dll`, `libEGL.dll`) приходят из `media_kit_libs_windows_video`, хотя видео в приложении нет. `audiotags.dll` (0,8 МБ) — пакет не используется (см. `dependencies.md`). Установщик сжимает всё это до 27,1 МБ.
- **Метаданные exe** (`windows/runner/Runner.rc`, с 2026-09-11): `CompanyName` = `Z43 Studios`, `ProductName` и `FileDescription` = `Protogenix`. Папка данных от них не зависит: путь задан явно (`data.md`).

## Платформы и каналы

Решения Orion (2026-09-11):
- Релизные платформы — **Android и Windows**.
- **iOS и macOS не поддерживаются.** Папки `ios/` и `macos/` остались от шаблона: в `Info.plist` нет фонового аудио (`UIBackgroundModes` → `audio`), в `Release.entitlements` нет `com.apple.security.network.client`. Время на них не тратить.
- **Linux** собирается, но ни разу не тестировался. Пока он не проверен, в релиз не включать.
- **Google Play не используется.** Android распространяется только своими каналами и обновляется встроенной обновлялкой, поэтому flavor'ы не нужны. К лучшему: правила Play запрещают и скачивание с YouTube, и самообновление в обход Play.

## Где хранить релизы

**Решение Orion (2026-09-11): только GitHub Releases.** Бесплатно, без лимитов, ничего не настраивать; кому GitHub недоступен, включит VPN. Манифест — ассет релиза, читается по `https://github.com/OrionZ43/protogenix/releases/latest/download/protogenix-update.json`: это обычная загрузка, а не API, поэтому лимита 60 запросов в час нет.

- Ядро обновлений всё равно принимает список адресов (для манифеста и для файлов). Сейчас в нём один GitHub; зеркало добавляется без переделки. Манифест подписан, у файлов есть SHA-256, поэтому зеркалам доверять не нужно.
- Токены для загрузки релизов (`gh auth`) и приватный ключ подписи манифеста хранятся только у Orion и никогда не попадают в git, логи или чат.

Что рассматривали и почему отказались (факты на 2026-09-11):
- **GitHub из России работает ненадёжно.** С мая 2026 доля неудачных соединений заметно выросла (по данным Meduza и OONI — 10–16%), в июле был масштабный сбой у российских провайдеров; Роскомнадзор блокировку отрицает. Принято: пользователи из России пользуются VPN.
- **Yandex Object Storage** — лучший вариант для России (бесплатно каждый месяц 100 ГБ трафика, 1 ГБ хранения, 100 000 GET и 10 000 PUT; дальше около 1 ₽/ГБ), но бакет нельзя создать без платёжного аккаунта в статусе `ACTIVE` или `TRIAL_ACTIVE`, а привязывать биллинг Orion не хочет. Нерезидентам РФ и Казахстана аккаунт к тому же подтверждают вручную, оплата в долларах.
- **Vercel Blob** на Hobby: 1 ГБ хранения, 10 ГБ трафика в месяц, при превышении отключается на 30 дней. Файлы с `*.public.blob.vercel-storage.com`, заливка `vercel blob put <файл> --access public`. Сам сайт `*.vercel.app` из России открывается (трафик сайта — 100 ГБ в месяц), а IP собственных доменов на Vercel бывают в блок-листах. Hobby — только некоммерческое использование.
- **GitFlic** — релизы с произвольными файлами есть, но скачивание без входа в аккаунт и прямые ссылки не проверены.
- **Google Диск и Яндекс Диск** — только для ручного скачивания. Постоянных прямых ссылок нет; Google Диск показывает страницу «не удалось проверить на вирусы» и режет популярные файлы по квоте, Яндекс Диск без платного тарифа ограничивает часто скачиваемую публичную ссылку на сутки.
